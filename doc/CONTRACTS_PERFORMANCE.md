# Critical Flows, Performance, gRPC Contracts, and Technical Evolution

## 1. Distributed Data Validation
Validation happens in parallel across two layers using *Blind Indexes*:
* **On the Front-end (Headless Player):** The field map is checked before submission. If there are errors, the interface blocks the submission immediately, saving bandwidth.
* **On the Back-end (Logic Engine):** The gRPC server always revalidates the payload against the schema saved in the database to prevent malicious submissions via the API. If it detects invalid data, it returns an error map structured by the `blind_index` of the failed component, allowing the front-end to flag the exact input without exposing real table structures.

## 2. Batched Rendering Strategy (Batching)
Due to the continuous stream of data generated by WebSockets and user actions, the *Headless Player* adopts a *batching* strategy on the Virtual DOM:
* The front-end accumulates all changes occurring within a **16-millisecond** window (aligned with the 60Hz refresh rate of monitors).
* The Virtual DOM's comparison algorithm (*Diffing*) runs **only once per batch**, applying a single optimized update to the real DOM, eliminating fluidity breaks (*jank*).

## 3. Instant Deploy and Rollback Mechanism
* **Interpreted Approach:** Publishing consists of creating a new row in a version history table (e.g., `versoes_sistema`) and switching a flag's state to *Ativa*. The *Headless Player* always consumes the version that has the active flag.
* **Millisecond Rollback:** If a new version presents failures, the reversion is executed by switching the status flag back to the previous stable version, with no need for recompilation or downtime.

## 4. Background Data Export Flow
| Flow Step | Technology / Pattern Applied | Technical Description |
| :--- | :--- | :--- |
| **1. Request** | Gateway (Go) -> Export Engine | The user clicks "Export". The system creates a Job and immediately frees up the front-end with a notification, avoiding timeouts. |
| **2. Collection** | gRPC Server Streaming | The *Export Engine* consumes UI, Rules, and Operational Records data in continuous *chunks* to avoid overloading RAM. |
| **3. Storage** | Cloud Storage (S3 / GCS) | The consolidated data is compressed into a file and stored in a secure, isolated cloud bucket. |
| **4. Secure Delivery**| Presigned URL (Temporary Link) | A fast-expiring encrypted link is generated. The user downloads the file directly from the cloud, saving the API Gateway's resources and bandwidth. |

## 5. Official Protocol Buffers Contract (`.proto`)
The standard communication between the Gateway Layer and the *Logic Engine* for form submission uses the **Unary RPC** mechanism. Collections of dynamic fields travel via `map<string, string>` structures binding the *Blind Index* to the filled-in text value.

```protobuf
syntax = "proto3";

package construtor.logic.v1;

// Represents the submission of dynamic operational data
message SalvarFormularioRequest {
  // Dynamic key-value map linking the input's Blind Index to the filled-in value
  map<string, string> dados_formulario = 1;
}

// Response with the validation and persistence status
message SalvarFormularioResponse {
  bool sucesso = 1;
  // Error map indexed by the Blind Index of the failed component
  map<string, string> erros_validacao = 2;
  string mensagem_status = 3;
}

service LogicEngineService {
  // Unary action to validate and write data to the shared database
  rpc SalvarFormulario (SalvarFormularioRequest) returns (SalvarFormularioResponse);
}
```

## 6. Future Evolution Roadmap: Compiled Approach
The current architecture is prepared to evolve into a hybrid or purely compiled model without needing to refactor the platform's core:
* The *Design Engine* and *Logic Engine* microservices will remain unchanged, as they continue to be the official repositories of business rules and screens.
* The *Deploy Engine* will be expanded to include automatic code generators.
* Upon clicking "Publish", the service will read the definitions via gRPC and trigger automated CI/CD pipelines to compile independent Docker images or cloud Serverless functions for specific customers (such as *Single-Tenant* instances or enterprise accounts) requiring full performance isolation, dedicated infrastructure, and native Kubernetes CPU/Memory limit enforcement.
